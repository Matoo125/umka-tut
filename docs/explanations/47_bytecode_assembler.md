# Exercise 47: Bytecode Assembler & Disassembler

## Objective

Implement a **Two-Pass Bytecode Assembler and Disassembler** in Umka and Lua. The program parses human-readable assembly source code with forward and backward jump labels (`loop:`, `body:`, `exit:`), resolves label target indices across two passes, emits binary instruction packets (`Instr{op, arg}`), and disassembles the binary instructions back into human-readable format.

---

## Core Concepts

### 1. Two-Pass Assembly Process
Single-pass assemblers struggle when branch instructions jump forward to labels that haven't been declared yet (the "forward reference problem"). A two-pass architecture cleanly solves this:
- **Pass 1 (Symbol Table Collection)**:
  - Scans lines sequentially.
  - Keeps an instruction pointer counter `instrCount`.
  - When encountering a label definition (e.g. `loop:`), records the label name and current `instrCount` into a symbol table.
  - When encountering an instruction, increments `instrCount`.
- **Pass 2 (Code Generation)**:
  - Scans instructions again.
  - Translates symbolic mnemonics (`PUSH`, `ADD`, `JNZ`) into integer opcodes.
  - Resolves operand arguments: numeric constants are parsed directly, while label names are looked up in the symbol table to emit absolute branch targets.

### 2. Disassembly Mechanics
Disassembly reconstructs readable assembly mnemonics from binary bytecode:
- Maps each opcode enum back to its string representation (`Opcode.OP_PUSH` $\to$ `"PUSH"`).
- Displays aligned memory addresses/offsets (`0000:`, `0001:`) alongside mnemonic names and operand arguments.

---

## Umka vs. Lua Implementation Nuances

| Feature | Umka | Lua |
| :--- | :--- | :--- |
| **Opcode Enumeration** | Strongly typed `type Opcode = enum { OP_PUSH, ... }` | Integer lookup table `Opcode = { OP_PUSH = 1, ... }` |
| **Symbol Table** | Struct array `[]LabelEntry{name, offset}` with linear scan | Hash table `labels[labelName] = instrCount` |
| **String Tokenization** | Custom scanner `splitTokens` using `slice(line, start, end)` | Pattern matching via `line:gmatch("%S+")` |
| **Instruction Layout** | Fixed struct `type Instr = struct { op: Opcode; arg: int }` | Table `{ op = op, arg = arg }` |

## Common Pitfalls

1. **Forward Jump References**: Single-pass parsing without backpatching cannot resolve jump targets declared later in the source file. Splitting analysis into label collection (Pass 1) and emission (Pass 2) prevents unresolved reference errors.
2. **Offset Increment on Labels**: Label definitions themselves do not occupy byte or instruction space in the generated bytecode. Do not increment the instruction counter when processing a label definition.
3. **Trailing Slices**: Remember that Umka's `slice(s, start, end)` takes exclusive end index, and string indices are 0-based.
